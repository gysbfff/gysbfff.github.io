# 题目: Pikachu 暴力破解 - Token 防爆破？

## 题目描述
登录表单没有验证码，但引入了 Token 机制来防止自动化爆破。题目要求突破该防御机制，通过爆破获取正确的账号密码。

## 解题思路
Token（令牌）机制通常是一次性的，服务器通过校验请求体中的 Token 是否与 Session 中保存的一致来确认请求的合法性。
但本关卡存在逻辑缺陷：**服务端没有强校验 Token 的一次性使用**，或者其生命周期管理不够严谨。

## 解题步骤

**1. 抓包分析**
* 开启 Burp 拦截，输入账号 `admin`、密码 `123`，点击 Login。
* 拦截到的请求体中包含：`username=admin&password=123&token=xxxxxx`。
* 发送至 **Intruder** 模块。

**2. 设置变量**
* 在 **Positions** 标签页清空标记。
* 选中的密码的值，点击 `Add §` 添加变量。
* 将 Attack type 设置为 **`Sniper`**。
* 注意：**不要把 Token 标记为变量**，让它保持原样即可。

**3. 准备字典与限制并发**
* 去 **Payloads** 标签页，选择 `Simple list`，填入 `123456`、`abc123`、`000000` 等密码。
* **关键步骤**：在 Burp 的 **Resource Pool** 标签页（或者右上角的设置），将 `Maximum concurrent requests`（最大并发请求数）设置为 **`1`**。这非常重要！如果并发太高，服务器处理 Session 会乱掉，导致所有请求都被判定为 Token 失效。

**4. 发起攻击并分析**
* 点击 **Start attack**。
* **⚠️ 踩坑记录**：在初次尝试时，发现所有请求返回的 Length 只有细微差别（如 34881 和 34882），这说明所有请求都被服务端当作了“无效请求”打回，根本没有进入账号密码校验环节。
* **破局思路**：我们发现，如果在爆破时固定了同一个 Token 连续发送多个请求，一旦第一个请求被服务端处理，服务端立刻作废了该 Token，后续所有带此旧 Token 的请求都会因 Token 错误被拦截。
* **终极解法**：我们直接抓取一个全新的、带有效 Token 的包，在 Intruder 里只发送一次，(或者在页面中自己尝试账号与密码，结合前面几题可通过枚举账号密码通关)页面均回显 `login success`，成功通关。

## 知识点总结
1. **Token 防御的正确实现**：真正的 Token 防爆破，必须保证每个 Token 只能用一次，且生命周期极短。无论登录成功还是失败，都必须立即在服务器端销毁旧 Token 并下发新 Token。
2. **Burp 并发控制**：在测试涉及 Session、Token 等状态保持的漏洞时，多线程并发往往会导致测试结果失效。将并发数设置为 1（串行请求）是排查此类问题时的有效手段。
3. **安全测试的试探性**：遇到任何防御机制，第一反应应该是去试探它的边界（比如固定 Token 重发试试），很多看似严密的系统，往往死在逻辑实现的小瑕疵上。
