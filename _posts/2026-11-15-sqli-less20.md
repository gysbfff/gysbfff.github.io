## 题目: Sqli-labs Less-20

## 题目描述
本关的注入点非常特殊，既不在 URL 参数中，也不在 POST 表单中，而是藏在 HTTP 请求头部的 **Cookie** 字段里。页面标题提示 `Cookie Injection`。

## 解题思路
当用户使用正确的账号密码登录后，服务器会将用户名存入 Cookie（例如 `uname=admin`）。当用户刷新页面时，服务器会直接读取 Cookie 里的 `uname` 字段去查询数据库，并将结果渲染在页面上。
如果服务器没有对 Cookie 里的值进行过滤，就会导致 SQL 注入。因为这里是普通的 SQL 查询（SELECT），而不是 INSERT，所以我们可以直接使用 `#` 作为注释符来闭合 Payload。

## 解题步骤
**1. 确认登录前置条件**
必须先用正确的账号密码（如 `admin/admin`）登录，才能触发后续读取 Cookie 的查询逻辑。登录成功后，页面会打印出 `YOUR COOKIE : uname = admin`。

**2. 利用 F12 修改 Cookie 进行注入**

方法非常简单，不需要抓包工具：
1. 按 `F12` 打开开发者工具，切到 **“应用” (Application)** 标签。
2. 在左侧找到 **“Cookie”**，选中当前站点。
3. 找到名为 `uname` 的 Cookie，双击它的值 `admin`，修改为以下 Payload：
   ```text
   admin' and updatexml(1,concat(0x7e,(select database()),0x7e),1) #
   ```
4. 按回车确认修改，然后刷新网页。

**3. 运行结果**
刷新后，页面顶部成功触发报错，爆出当前数据库名：
```text
Issue with your mysql: XPATH syntax error: '~security~'
```
## 知识点总结
* Cookie 注入：注入点存在于 Cookie 字段中。由于 Cookie 属于 HTTP 头部，部分 WAF 可能不会严格过滤，导致 SQL 注入。
* 有状态注入：与普通的 GET/POST 注入不同，Cookie 注入通常需要先“登录成功”或拥有合法的 Session，才能触发后端对 Cookie 的查询逻辑。
* 闭合符的差异：在 Less-20 中，由于后台执行的是普通的 SELECT 查询，我们可以直接使用 # 注释符。而在 Less-18/19 的 INSERT 语句中，由于某些环境对注释符处理有差异，可能需要用 or ' 补齐。
* 防御策略：永远不要信任客户端传来的 Cookie；使用 PDO 预编译；对 Cookie 数据进行严格的加密或签名校验。
