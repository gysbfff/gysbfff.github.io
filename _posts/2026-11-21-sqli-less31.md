## 题目: Sqli-labs Less-31

## 题目描述
页面提示 `Please input the ID as parameter with numeric value`，同时赫然写着 `This Site Protected by World's Best WAF`。
本关是 Less-30 的变种，继承了它的“视觉欺骗”属性，并且在闭合方式和空格过滤上做了极限升级。

## 核心原理与绕过策略
通过黑盒盲打和报错回显，我推断出了这关极其阴险的防御机制：
1. **闭合方式**：这关既不是单引号，也不是双引号，而是**双引号加括号**（`id=("$id")`），必须用 `")` 进行闭合。
2. **空格封杀**：WAF 拦截了常规的空格，无法使用标准语法。
3. **无注释符闭合**：注释符 `--+` 和 `#` 大概率被拦截或无法起到断句作用。

**绕过策略：**
* 用 `")` 闭合前半截。
* 用 `%0a`（换行符）完美替代所有空格。
* 在 Payload 末尾使用 `||("` 与后台原本的 `") LIMIT 0,1` 缝合，形成合法的逻辑闭环。

## 解题步骤
**1. 验证闭合与报错（摸底）**
直接在地址栏输入，注意这里是 `"` 和 `)`：
```text
http://127.0.0.1/sqli-labs/Less-31/?id=1") and 1=1 --+
```
如果页面正常回显了 Dumb，说明闭合符完美命中，且没有被拦截。

**2. 探测回显点**
这关最恶心的地方在于它可能连 union select 的空格都过滤了。我决定先用最稳妥的报错注入：
```text
http://127.0.0.1/sqli-labs/Less-31/?id=1") and updatexml(1,concat(0x7e,database()),1) --+
```
如果页面弹出了 XPATH syntax error: '~security~'，说明这关连 WAF 都没有，可以直接脱库。
(⚠️ 但实际测试发现，它并没有回显报错，说明 updatexml 被屏蔽或转义了。这也意味着我们必须回到联合查询，并想办法绕过它的空格过滤。)

**3. 联合查询极限绕过（终极脱库）**
报错注入被吞，且常规空格被拦截，我使用了 %0a（换行符）替代所有空格，将 union、select、from、where 隔开，并在末尾使用 ||(" 进行对称闭合。
Payload：
```
?id=-1")union%0aselect%0a1,group_concat(username,0x3a,password),3%0afrom%0ausers%0awhere%0a(1=1)||("
```
**回显现象**：页面瞬间爆出所有账号密码（包括之前注入留下的毒账号 admin'# 等）。

## 踩坑记录与复盘
* **视觉欺骗**：千万不要被页面上“WAF”或“安全防护”的字样吓住。黑盒测试中，一切以实际发包结果为准。
* **报错注入的局限性**：在面对 id=("$id") 且开启了某些 WAF 保护的环境时，updatexml 可能会被直接拦截或无法回显，此时必须果断切换到联合查询。
* **%0a 的妙用**：当 WAF 拦截了空格和 Tab 时，%0a（换行符）往往是最后的破局利器，它可以完美分割 SQL 语法元素。
* **对称闭合的艺术**：当注释符失效时，精准推算出后端的括号闭合结构，用 ||(" 强行缝合，是完成注入的最后一把钥匙。

## 知识点总结
* **双引号括号闭合**:应对 id=("$id") 这种极度特殊的闭合结构。
* **WAF 极限绕过**：%0a 替代空格是无视 WAF 空格拦截的最优解。
* **联合查询脱库**：在确定没有关键字过滤时，联合查询永远是最高效的脱库手段。
