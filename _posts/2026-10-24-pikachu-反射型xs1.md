# 题目：Pikachu  Cross-Site Scripting - 反射型XSS(get)

## 题目描述
页面提供了一个输入框，询问你喜欢的 NBA 球员。输入内容提交后，会直接显示在页面上。要求利用反射型 XSS 漏洞，让页面弹出一个警告框（如 `alert(1)`）。

## 解题思路
反射型 XSS 的特点是：用户输入的数据没有经过严格的过滤，直接被服务端输出到了 HTML 页面中。由于本关是通过 GET 请求提交参数，我们可以通过修改 URL 中的参数值来注入并执行 JavaScript 代码。

## 解题步骤

**1. 正常测试与寻找注入点**
*   在输入框中输入普通字符（如 `kebi`），点击 submit，页面回显 `who is kebi,i don't care!`。
*   观察 URL，发现参数是通过 GET 传递的：`?message=kebi&submit=submit`。

**2. 尝试直接注入**
*   尝试在输入框输入经典的 Payload：`<script>alert(1)</script>`。
*   **⚠️ 踩坑记录**：发现输入框有长度限制（前端 `maxlength` 属性限制），无法完整输入长代码；或者前端做了某些转义，导致提交后页面没有弹窗，只有残缺的代码被拼接到页面上。

**3. 绕过前端限制**
*   既然前端限制了输入框，我们就直接利用 GET 请求的特性，在浏览器的地址栏中修改 URL 参数。
*   将 `message=` 后面的内容替换为完整的 Payload：
  `http://127.0.0.1/pikachu/vul/xss/xss_reflected_get.php?message=<script>alert(1)</script>&submit=submit`
*   按下回车键，浏览器成功弹窗，XSS 注入成功！

**4. 🎁 意外发现的隐藏彩蛋**
*   在测试过程中，我在输入框尝试输入了 `kobe`，意外触发了一个隐藏页面。
*   系统并没有直接回显文字，而是渲染了一张科比的海报，并配文“愿你像kobe一样，永远年轻，永远热血沸腾！”。
*   **源码分析思考**：这说明开发者在后端代码中使用了类似 `if ($message == 'kobe')` 的硬编码逻辑。这个彩蛋虽然暖心，但也反映了一个隐患：如果攻击者构造类似 `kobe<script>alert(1)</script>` 的 Payload，虽然字符串不完全等于 `kobe` 不会触发海报，但如果代码逻辑不严谨，极易产生意料之外的漏洞执行。

## 知识点总结

1. **反射型 XSS (Reflected XSS)**：属于非持久型攻击。恶意代码隐藏在 URL 中，一旦受害者访问该链接，服务器会将代码反射回浏览器执行。由于需要诱导点击，通常利用钓鱼链接等方式进行传播。
2. **前端校验的脆弱性**：前端的 `maxlength` 属性、输入框长度限制等都是不可信的。攻击者可以通过抓包（Burp Suite）、修改 URL 等方式绕过这些限制，直接将数据发给服务端。
3. **防御策略**：
   *   **输入过滤与输出编码**：最根本的防御手段。在数据输出到 HTML 页面之前，必须使用 HTML 实体编码（如将 `<` 转义为 `&lt;`），确保浏览器将其视作普通文本而非可执行代码。
   *   **设置 HttpOnly**：给 Cookie 设置 `HttpOnly` 属性，即使发生 XSS 漏洞，JS 也无法读取到用户的敏感 Cookie 信息，降低危害。
