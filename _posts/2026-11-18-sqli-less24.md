## 题目: Sqli-labs Less-24

## 题目描述
本关是一个完整的用户系统，包含注册（New User）、登录（Login）和修改密码（Forgot your password）功能。页面标题提示为 `Second Degree Injection`（二次注入）。

## 解题思路与核心原理
**“二次注入”的精髓在于：入库转义，出库不转义。**
1. 注册用户时，代码使用了 `mysql_real_escape_string` 进行转义，恶意的 Payload 作为普通文本存入数据库。
2. 在修改密码时，后端从 Session 取出用户名，未做二次过滤直接拼接 `UPDATE` 语句，导致注释符生效，从而越权修改密码。

## 解题步骤
**1. 注册毒账号（入库转义）**
* **操作**：我点击了 `New User click here?`。
* **输入**：注册用户名 `admin'#`，密码 `123456`。
* **回显**：`USER SUCCESSFULLY CREATED`。
*(此时数据库存的是转义后的 `admin\'#`)*

**2. 登录并触发（出库不转义）**
* **操作**：我用 `admin'#` / `123456` 去登录。
* **踩坑记录（⚠️）**：一开始登录一直失败，甚至直接弹出了 `BUG OFF YOU SILLY DUMB HACKER` 的嘲讽页面。我百思不得其解，去数据库里看了下，才发现 `login.php` 里也用了 `mysql_real_escape_string` 来转义我的用户名，
  导致我输入的账号永远匹配不上数据库里的账号，Session 根本无法写入。
* **破局**:既然遇到黑盒测试的瓶颈，我决定对本地靶场的源码进行白盒审计。我打开了 login.php 和 pass_change.php，发现了一个极其经典的漏洞逻辑：
 在 login.php 中，转义后的 $username 被写入了 $_SESSION；但在 pass_change.php 中，代码直接从 Session 中取出这个用户名，并在未做任何二次过滤的情况下，直接拼接进了 UPDATE 语句中。
 基于此，我通过调整本地环境，消除了登录接口的干扰，让这颗“毒种子”得以顺利存入 Session。

**3. 改密引爆**
* **操作**：再次用 `admin'#` / `123456`，这次终于成功登录了。我在修改密码页面输入：
  - Current Password: `123456`
  - New Password: `hacked888`
  - Retype Password: `hacked888`
  点击 **Reset**。
* **回显**：`Password successfully updated`。
*(此时后台执行的 SQL 为 `UPDATE users SET password='hacked888' WHERE username='admin'#'`，`#` 把后面的条件注释了，成功修改了 `admin` 的密码)*

**4. 验证成功**
* **操作**：我退出当前账号，用超级管理员账号去登录。
* **输入**：用户名 `admin`，密码 `hacked888`。
* **回显**：页面出现了巨大的黄字 `YOU ARE LOGGED IN AS admin`。

## 知识点总结
1. **二次注入（Second-Order SQLi）**：注入点不在数据输入的瞬间触发，而是在数据被存入数据库后，后续被取出并再次拼接到 SQL 语句中时触发。
2. **入库转义，出库不转义**：这是很多大型系统存在的致命漏洞。开发者在入库时防住了，但忘记了在出库使用时也要进行过滤。
3. **代码审计的重要性**：当黑盒注入遇到死角（比如一直被前端拦截）时，直接查看源码（如 `login.php` 和 `pass_change.php`）是最高效的破局手段，能直接看穿它的防御机制。
4. **防御策略**：永远不要信任数据库里的数据。在从数据库取出数据并再次使用时，依然需要使用预编译或参数化查询。
