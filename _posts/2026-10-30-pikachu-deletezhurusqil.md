## 题目: Pikachu SQL Inject - Delete 注入

## 题目描述
页面是一个“不正经的留言板”。要求利用 SQL 注入漏洞，在删除留言时，通过 DELETE 语句注入恶意代码，破坏或获取数据。

## 解题思路
后端的删除逻辑通常为 `DELETE FROM message WHERE id = $id`。如果 `id` 未过滤，就可以构造永真条件（如 `or 1=1`），删除整个表的数据。
本关在尝试黑盒注入时遭遇了服务器层级的严格拦截（400报错），随后通过**源码审计**确认漏洞存在，并通过报错信息推断出参数为**数字型**，最终成功实现全表删除。

## 解题步骤

**1. 正常留言与抓包**
* 在留言板输入 `test` 并提交，页面下方显示留言，并附带“删除”按钮。
* 开启 Burp 拦截，点击“删除”，抓到一个 GET 请求：`GET /.../sqli_del.php?id=56 HTTP/1.1`。注入点锁定为 `id` 参数。

**2. 遭遇 WAF 拦截（⚠️ 踩坑记录）**
* 在 Burp 中修改 `id` 为 `56 or 1=1` 放行，页面直接返回 `HTTP 400 - Bad Request`。
* **原因分析**：本地 Apache/PHP 环境配置了严格的安全规则，直接拦截了包含空格和 `or` 等敏感字符的 URL 请求。

**3. 源码审计与类型反转（⚠️ 核心突破）**
* 进入靶场源码目录，打开 `sqli_del.php`，确认 `$query = "delete from message where id = $id";`。这说明 `id` 确实是直接拼接的，漏洞存在。
* 尝试在 URL 中注入 `id=60' or '1'='1`，页面报错 `near '' or '1'='1'`。
* **真相大白**：报错信息直接暴露了后端代码是 `WHERE id = $id`，这是一个**数字型**的 DELETE 注入，根本不需要单引号闭合！之前的单引号导致语法断裂。

**4. 构造最终 Payload 实施攻击**
* 去掉单引号，直接拼接逻辑表达式（利用 URL 编码的空格 `%20` 绕过 WAF）：
  `id=60 or 1=1`
* 因为 `1=1` 永远为真，`DELETE` 语句忽略了前面的 ID，成功将 `message` 表中的所有数据一次性清空。
* 页面提示 `删除失败,检查下数据库是不是挂了`。这并非真正的失败，而是因为表已被删空，后端 `affected_rows` 返回 0 触发的提示，侧面印证了注入成功。

## 知识点总结
1. **数字型与字符型的区分**：数字型不需要引号，字符型需要。可以通过报错信息（如 `near ''`）快速判断，避免无效尝试。
2. **DELETE 注入的毁灭性**：一旦注入 `or 1=1` 这样的永真条件，会导致全表数据被清空（删库跑路）。
3. **代码逻辑的盲区**：后端通过 `affected_rows` 判断是否成功，当数据已经被删空时，反而会提示失败。实战中可作为“漏洞已触发”的另类信号。
4. **防御策略**：严格使用 `intval()` 将 ID 强制转换为整数；使用 PDO 预编译；限制数据库账号的 `DELETE` 权限。
